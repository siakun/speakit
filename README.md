# speakit

<!-- INTENT: 알고 있는 개념을 면접관에게 정돈된 문장으로 말하는 연습에 집중한다. 문제 목록이나 성취 지표를 첫 화면에 늘어놓지 않고 질문 한 장, 직접 한 자기 점검, 이어지는 꼬리 질문을 중심에 둔다. -->
CS 질문을 보고 소리 내어 설명한 뒤, 카드를 뒤집어 평가 기준과 대조하는 모바일 웹앱입니다. 마크다운으로 쓴 질문 노트에서 질문, 평가 기준, 서로 다른 답변과 꼬리 질문을 읽어 카드로 만들고, 앱에서 이어서 연습합니다. 앱 화면에는 `기초질문`이라는 이름으로 표시합니다.

배포한 사이트는 https://siakun.github.io/speakit/ 에서 엽니다.

## 실행

저장소 루트에서 실행합니다. Node.js 요구 버전은 `package.json`의 `engines`를 따릅니다.

```powershell
npm install
npm run dev
```

질문 노트를 지정하지 않으면 샘플 덱으로 실행합니다. 실제 노트를 읽게 하는 방법은 [질문 노트](#질문-노트)에 있습니다.

터미널에 표시된 Local 주소를 PC에서 엽니다. iPhone에서는 같은 Wi-Fi에 연결한 뒤 Network 주소를 Safari에서 엽니다. Windows 방화벽이 연결을 막으면 개인 네트워크의 Node.js 연결 허용 상태를 확인합니다. 외부 공개나 터널 연결은 실행 명령에 포함하지 않습니다.

배포용 정적 파일은 `npm run build`로 만들고 `npm run preview`로 확인합니다. 개발 서버는 저장소 폴더를 웹 루트로 사용하며, 질문 노트에서는 콘텐츠 플러그인이 추출한 필드만 전달합니다. 호스팅할 때는 `dist`를 사용합니다. 자산 경로가 상대 경로라서 `dist`는 도메인 루트와 하위 경로 어느 쪽에 올려도 동작합니다.

실기기의 애니메이션 성능은 배포용 미리보기에서 확인합니다. 주소 끝에 `?fps=1`을 붙이면 JavaScript의 `requestAnimationFrame` 호출 주기를 표시합니다. `p95`는 측정한 간격 중 95%가 그 값 이하라는 뜻입니다. 기본 스크롤은 이 콜백과 독립적으로 처리되므로, 표시된 수치를 가로 또는 세로 스크롤의 실제 fps로 해석하지 않습니다. 짧은 표본은 수치 대신 측정 구간 부족으로 표시합니다. 매개변수를 지우면 진단 코드도 불러오지 않습니다.

## 사용

질문 카드를 탭하면 답변 기준이 나타납니다. 말했던 항목을 체크하고 빠뜨린 내용의 꼬리 질문을 눌러 이어서 연습합니다. 카드 상단의 질문을 탭하면 다시 앞면으로 돌아갑니다.

좌우 스와이프와 하단 화살표로 질문을 넘깁니다. 한 회차 안에서는 질문이 중복되지 않으며, 마지막 질문 뒤에서 다시 섞어 시작합니다. 오른쪽 위의 분야 선택에서 질문을 검색하거나 분야를 바꿉니다. 책갈피로 저장한 질문은 같은 메뉴의 `다시 볼 질문`에서 모아 봅니다.

답변 기준은 원본의 `평가 체크리스트`입니다. `1질문 3답변`은 모범 답안이 아니라 키워드에 따라 꼬리 질문이 달라지는 모습을 보여 주는 비교 자료입니다. 오류, 빠뜨린 항목과 가상의 경험담이라는 구분을 유지합니다. 원본의 `답변` 절도 완성을 보장하지 않으므로 작성 중인 노트로 표시합니다. 꼬리 질문에 답이 없으면 그 상태를 그대로 알립니다.

책갈피, 체크한 항목, 분야와 질문 위치는 같은 브라우저의 localStorage에 저장합니다. 브라우저 데이터를 삭제하면 기록도 사라집니다. 체크는 자기 점검이며 자동 채점이 아닙니다. 녹음, STT, AI 피드백은 아직 구현하지 않았습니다.

## 질문 노트

<!-- 질문 노트는 앱과 따로 쓰고 고치는 원본이며, 사이트에 싣지 않는 메모도 함께 담긴다. 앱 저장소에 사본을 두면 같은 노트를 두 곳에서 관리하게 되고 원문 전체가 공개되므로, 앱은 빌드하는 순간에만 노트 폴더를 읽고 아래 표의 필드만 싣는다. -->
질문 노트는 이 저장소에 두지 않습니다. 앱은 `SPEAKIT_CONTENT_DIR`가 가리키는 폴더를 읽습니다. 그 폴더의 하위 폴더 하나가 분야 하나이고, 하위 폴더 안의 마크다운 파일 하나가 질문 카드 하나입니다. 폴더 바로 아래에 있는 파일은 읽지 않습니다.

경로를 지정하지 않으면 `sample-content`의 샘플 덱을 읽습니다. 샘플 덱은 형식 확인과 브라우저 검사에 쓰는 가짜 데이터입니다. 실제 노트로 실행하려면 저장소 루트에 `.env.local`을 만들고 노트 폴더의 경로를 적습니다. `.env.local`은 Git에서 제외됩니다.

```
SPEAKIT_CONTENT_DIR=C:/path/to/notes
```

앱은 노트 파일에서 아래 표의 `##` 절만 읽고, 표에 없는 절과 `<!-- -->` 주석은 읽지 않습니다. 형식의 예는 `sample-content`에 있습니다.

| 절 | 카드에서 쓰는 곳 |
|---|---|
| `기초질문` | 첫 인용문(`>`)이 카드 앞면의 질문. 없으면 빌드 오류 |
| `평가 체크리스트` | `- [ ] **항목 이름**: 기준` 항목과 그 아래의 `- 알아야 할 내용:`, `- 빠뜨리면:`이 답변 기준과 꼬리 질문. 하위 항목이 빠지면 빌드 오류 |
| `1질문 3답변` | `###` 제목마다 인용문은 비교 답변, 그 아래 목록은 답변 메모 |
| `꼬리 질문` | `###` 제목이 질문, 본문이 답변. 본문이 없으면 답변이 아직 없다고 표시 |
| `답변` | 작성 중인 답변 노트 |
| `참고자료` | 답변 기준 아래의 참고자료 |
| `기출` | 내용은 싣지 않고 기출 여부만 기록 |

## 배포

`main`에 push하면 `.github/workflows/deploy.yml`이 GitHub Pages에 배포합니다. 워크플로는 콘텐츠 저장소에서 노트 폴더만 sparse checkout으로 받고, `npm test`로 노트 형식을 검사한 뒤 빌드합니다. 노트만 바뀌었을 때는 이 저장소에 커밋이 없으므로 직접 다시 배포합니다.

```powershell
gh workflow run deploy.yml -R siakun/speakit
```

콘텐츠 저장소는 비공개이므로 워크플로는 그 저장소에 읽기 전용으로 설치한 GitHub App의 토큰으로 노트를 받습니다. 이 저장소의 Actions 설정에 다음 두 값이 필요합니다.

- 변수 `CONTENT_READER_CLIENT_ID`: GitHub App의 Client ID
- 시크릿 `CONTENT_READER_APP_KEY`: GitHub App 개인키(.pem 파일 내용 전체)

배포한 사이트는 누구나 볼 수 있습니다. 카드에는 [질문 노트](#질문-노트)의 표에 있는 필드만 실리고, `기출` 절의 내용과 표에 없는 절, 주석은 실리지 않습니다. 공개하지 않을 노트는 노트 폴더 밖에 둡니다. CI 빌드는 노트 폴더를 지정하지 않으면 샘플 덱으로 대신하지 않고 실패합니다.

## 원본과 구현 경계

콘텐츠 변환 규칙은 `scripts/content.mjs`에 있고, 노트를 읽을 폴더는 `scripts/content-config.mjs`가 정합니다. 개발 서버가 원본 변경을 감지하고, 빌드할 때도 원본을 다시 읽습니다. 질문 목록을 먼저 읽고 현재 카드의 평가 기준과 비교 답변을 따로 불러옵니다. 생성한 질문 사본을 별도로 편집하지 않습니다. 현재 질문 수와 분야는 `npm run content:check`로 확인합니다.

화면은 React와 TypeScript, 개발과 정적 빌드는 Vite를 사용합니다. 콘텐츠 타입과 학습 기록 타입을 분리해, 향후 녹음과 전사 결과를 추가해도 질문 원본이나 직접 체크한 기록을 자동 평가 결과로 덮어쓰지 않도록 합니다. 음성 파일과 비동기 평가를 붙일 때는 별도의 시도 기록, 저장 정책과 서버 인증을 설계합니다.

카드는 브라우저 기본 가로 스크롤과 CSS Scroll Snap으로 이동합니다. 손가락 추종, 관성과 카드 정렬은 브라우저가 처리하며 JavaScript로 매 프레임 위치를 바꾸지 않습니다. 이웃 카드가 함께 움직이고, 한 번의 스와이프가 다음 카드의 정렬 지점을 지나치지 않도록 설정합니다. 이동 중에도 다시 잡아 방향을 바꿀 수 있으며 하단 버튼은 같은 영역에 기본 부드러운 스크롤을 요청합니다. PC에서는 하단 버튼이나 가로 휠과 트랙패드로 이동합니다. 답변이 펼쳐진 카드는 화면을 벗어날 때까지 내용을 유지합니다. 선택과 정착의 동기화는 `src/CardCarousel.tsx`에서 관리합니다.

다른 앱에 같은 구조를 적용할 때는 [iPhone 웹앱의 120fps 스크롤 구현 가이드](docs/ios-native-scroll-snap.md)를 참고합니다. 최소 예제, 카드 상태 설계와 실제 표시 프레임을 구분하는 검증 절차를 제공합니다.

화면 밖의 카드도 이동 거리를 계산할 슬롯은 유지하지만, 3D 카드 내용은 화면에 보이는 카드와 이웃에만 만듭니다. 연속 이동 중에는 현재 위치부터 목적지까지 준비해 중간 카드가 빈 채로 지나가지 않게 합니다. 매 프레임 React 상태를 갱신하지 않고, 보이는 슬라이드가 바뀔 때 렌더링 범위를 조정합니다.

[가로 카드 UI와 렌더링 최적화 가이드](docs/horizontal-card-ui-and-windowing.md)는 한 장에 집중하는 배치, 세 장을 기본으로 하는 렌더링 범위, 이동 중 예외 처리와 카드 상태 보존을 설명합니다.

카드의 가로 이동과 답변의 세로 스크롤은 중첩된 기본 스크롤 영역에서 처리합니다. 터치 이벤트를 취소하거나 화면 가장자리 제스처를 별도로 흉내 내지 않습니다. 보조 화면은 닫기 버튼과 아래로 끌어 닫기를 지원하는 모달이며, 터치 조작의 대체 버튼과 키보드 접근도 제공합니다. iPhone 안전 영역과 동작 줄이기 설정을 반영합니다.

## 검증

```powershell
npm test
npm run build
npx playwright install chromium webkit
npm run test:e2e
```

콘텐츠 검사는 샘플 덱과 지정한 질문 노트 각각에서 평가 기준 누락, 비교 답변 구분과 주제 간 중복을 확인합니다. 브라우저 검사는 내용이 고정된 샘플 덱으로 검사 전용 개발 서버(5174 포트)를 띄우고, 모바일 크기에서 탭, 스크롤, 검색, 책갈피와 재접속을 확인합니다. 슬라이드 검사는 기본 터치와 휠 입력 중 양쪽 카드의 실제 위치, 이동 중 재입력, 나가는 답변의 보존과 화면 크기가 달라진 뒤의 정렬을 확인합니다. 자동 캡처와 실행 결과는 Git에서 제외한 `.captures`와 테스트 결과 폴더에 저장합니다. Playwright의 모바일 환경과 WebKit 검증은 실제 iPhone Safari의 시스템 제스처와 주소창 동작을 완전히 재현하지 않으므로 실기기 확인도 필요합니다.
